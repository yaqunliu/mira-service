# 第一章：常见 Agent 架构模式

---

## 1.1 ReAct 模式

**Reasoning + Acting 交替循环**

```
Thought → Action → Observation → Thought → ...
```

**特点**：
- LLM 自主决定何时调用工具
- 每次观察后重新思考
- 适合**探索性任务**

**示例**：
> 用户：帮我查一下项目进度，如果角色图还没生成就开始生成

---

## 1.2 Plan-and-Execute 模式

**先规划，后执行**

```
Planner(生成计划) ──→ Executor(逐步执行)
```

**特点**：
- 计划可预览、可修改
- 执行过程确定性高
- 适合**复杂多步骤任务**

**示例**：
> 用户：帮我一键生成整个漫剧

---

## 1.3 Supervisor-Worker 模式

**中央调度 + 专业分工**

```
            ┌──────────────┐
 ┌──────────│  Supervisor  │──────────┐
 │          └──────────────┘          │
 ▼               ▼               ▼
Worker1       Worker2        Worker3
```

**特点**：
- 职责清晰，便于维护
- Supervisor 统一决策
- 适合**流程化生产任务**

---

## 1.4 模式对比

| 模式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| ReAct | 灵活、自主 | 不可控 | 探索性查询 |
| Plan-Execute | 可预览 | 规划开销大 | 复杂任务 |
| Supervisor | 职责清晰 | 需设计调度 | 流程化生产 |
| Workflow | 确定性高 | 不灵活 | 标准化流程 |

# 第二章：漫剧创作业务流程

---

## 2.1 完整创作链路

```
📜 剧本上传
     ↓
🔍 剧本分析 ──→ 识别角色 + 识别场景
     ↓
🎨 资产生成（角色图 + 场景图）
     ↓
📽️ 分镜设计（脚本 + 提示词）
     ↓
🖼️ 分镜图生成（首帧 + 尾帧）
     ↓
🎬 分镜视频生成
     ↓
🔊 音频处理 + ✂️ 最终合成
```

---

## 2.2 剧本分析阶段

**输入**：用户上传的剧本文本

**输出**：
- 角色列表（姓名、性别、年龄、外貌、性格）
- 场景列表（名称、环境、时间、氛围）

**技术要点**：
- LLM 结构化输出（JSON Schema）
- 多轮提取保证完整性

---

## 2.3 资产生成阶段

**角色/场景提示词生成**：

```
角色名 + 外貌描述 + 风格设定
          ↓
   LLM 生成英文 Image Prompt
          ↓
   调用图片生成模型
```

**支持功能**：
- 异步任务 + 轮询状态
- 支持重新生成和手动修改

---

## 2.4 视频生成模式

**三种生成模式**：

| 模式 | 输入 | 适用场景 |
|------|------|----------|
| **首尾帧模式** | 首帧图 + 尾帧图 | 动作连贯 |
| **仅首帧模式** | 首帧图 + 提示词 | 自由运动 |
| **参考图模式** | 参考图 + 提示词 | 风格参考 |

**视频提示词**：
```
主体运动 + 镜头运动 + 环境变化
```

# 第三章：为什么选择 Supervisor

---

## 3.1 业务特点分析

**漫剧创作的核心挑战**：

✅ **流程明确**：剧本→角色→分镜→视频

✅ **需要人工介入**：每个阶段需要用户确认

✅ **任务可拆分**：每个阶段职责单一

✅ **需要灵活跳转**："重新生成某个角色"

---

## 3.2 为什么不选 Workflow？

**Workflow 的问题**：

```
A ───→ B ───→ C ───→ D
```

❌ 用户说"跳过这一步"怎么办？

❌ 某个节点失败，整个流程卡死

❌ 新增一个阶段需要改动大量代码

---

## 3.3 为什么不选纯 ReAct？

**纯 ReAct 的问题**：

❌ LLM 可能"自由发挥"，跳过重要步骤

❌ 每次执行路径都不一样，调试困难

❌ Token 消耗大

❌ 可能陷入死循环

---

## 3.4 Supervisor 的优势

✅ **统一决策点**：便于控制流程

✅ **职责清晰**：每个 Worker 专注自己的任务

✅ **灵活跳转**：可以决定下一步去哪

✅ **易于扩展**：新增 Worker 只需注册

✅ **HITL 友好**：统一管理人工介入点

# 第四章：我们的架构设计

---

## 4.1 双层 Graph 架构

```
┌─────────────────────────────────────────┐
│           主图 (DialogueGraph)           │
│                                         │
│  entry → intent_detection               │
│              ↓                          │
│    ┌────────┼────────┐                  │
│    ▼        ▼        ▼                  │
│  query  子图执行   clarify              │
│           ↓                             │
│   ┌─────────────────────┐               │
│   │ ComicDramaSubgraph  │               │
│   │  Supervisor ⇄ Workers│              │
│   └─────────────────────┘               │
└─────────────────────────────────────────┘
```

---

## 4.2 Supervisor-Worker 调度

```
           ┌────────────────┐
           │   Supervisor   │
           │    (决策中心)   │
           └───────┬────────┘
                   │
    ┌──────────────┼──────────────┐
    ▼              ▼              ▼
script_analyst  asset_designer  storyboard
    │              │              │
    └──────────────┴──────────────┘
                   │
           返回 worker_result
                   ↓
              再次决策...
```

---

## 4.3 Worker 节点列表

| Worker | 职责 |
|--------|------|
| `script_analyst` | 剧本分析，提取角色场景 |
| `asset_designer` | 生成角色/场景/分镜图 |
| `storyboard_director` | 分镜脚本创作 |
| `audio_engineer` | 音频处理 |
| `video_editor` | 视频生成 |
| `asset_regenerator` | 资产重新生成 |

---

## 4.4 Supervisor 决策机制

**强制工具调用**：
```python
tool_choice = {
    "type": "function", 
    "function": {"name": "supervisor_decision"}
}
```

**决策输出**：
```python
{
    "next_worker": "asset_designer",
    "needs_input": False,
    "board_actions": [...],
    "response_text": "正在生成..."
}
```

# 第五章：踩过的坑

---

## 5.1 从 Workflow 到 Supervisor

**最初的设计**：
```
script → asset → storyboard → video（固定流程）
```

**遇到的问题**：
- 用户说"跳过"→ 无法处理
- 节点报错 → 整个流程卡死
- 新增功能 → 大量条件判断

**解决方案**：
重构为 Supervisor，所有决策集中处理

---

## 5.2 Supervisor 决策不准

**现象**：
```
用户：继续生成
预期：调度 asset_designer
实际：调度了 script_analyst（重复分析）
```

**解决方案**：
1. **状态注入**：注入 production_stage
2. **Prompt 硬规则**：明确阶段→动作映射
3. **强制工具调用**：结构化输出

---

## 5.3 内部逻辑暴露

**现象**：
```
用户看到：
"JSON 解析结果，image_prompt 字段..."
"调用 query_characters 返回了..."
```

**解决方案**：
```python
# 可见性白名单
RESPONSE_TEXT_NODES = {"supervisor", "clarify"}

# 只有白名单节点才能发消息
```

---

## 5.4 Tool 调用失败

**现象**：
- 图片生成超时 → 节点卡死
- 数据库失败 → 状态丢失

**解决方案**：

1. **工具级容错**：try-catch + 返回 error
2. **节点级回滚**：回退到上一稳定阶段
3. **超时保护**：asyncio.timeout(300)

---

## 5.5 迭代轮数过多

**现象**：
```
ReAct 循环 1/25...
ReAct 循环 23/25...
GraphRecursionError!
```

**解决方案**：
1. **批量处理**：一次调用处理多个资产
2. **提高限制**：recursion_limit = 50
3. **合并工具**：submit_batch_images()

---

## 5.6 AI 编码问题

### 问题 1：Bug 修不好
```
修 A → 引入 B → 修 B → A 又出现
```
**方案**：让 AI 先阅读完整代码，小步验证

### 问题 2：代码冗余
**方案**：定期审视，抽取公共函数

### 问题 3：修 Bug 引入新 Bug
**方案**：每次修改后跑完整测试

---

## 5.7 经验总结

| 问题 | 解决思路 |
|------|----------|
| 架构僵化 | 重构为灵活模式 |
| 决策不准 | 状态注入 + 硬规则 |
| 信息泄露 | 白名单过滤 |
| 异常处理 | 多层容错 |
| 性能问题 | 批量处理 |
| AI 编码 | 充分上下文 + 分步验证 |

---

# 总结

---

## 核心收获

1. **架构选型匹配业务**
   - 流程化 → Supervisor
   - 探索性 → ReAct

2. **Prompt 是核心竞争力**
   - 明确规则比"智能"更可靠

3. **异常处理前置设计**
   - 优雅降级好过直接崩溃

4. **AI 编码需要把关**
   - 充分上下文 + 小步快跑
